# Test Plan

## Strategy
Test pyramid with real infrastructure where it matters: unit tests for business logic, integration tests against a **real PostgreSQL** (Testcontainers) for APIs, migrations, RLS and workflows, Playwright end-to-end tests for critical journeys, axe-core accessibility checks, and dedicated security suites. CI blocks merges on failure.

## Test types and ownership
| Type | Tool (planned) | Scope |
|---|---|---|
| Unit | Vitest | Matching scoring, pricing and fee rules, workflow transition rules, validators, permission evaluation |
| Integration | Vitest + Testcontainers | API routes with auth, DB constraints, migrations up from empty, workflow transactions, notifications queue |
| Tenant isolation | Vitest + Testcontainers | For every tenant-owned table: cross-tenant select, insert, update, delete all denied; new table without policy fails |
| Authorization matrix | Vitest | Each route against each seeded role and scope: allowed, denied, hidden (404) |
| End-to-end | Playwright | Critical journeys below on desktop and mobile viewports |
| Accessibility | axe in Playwright + manual | Every page in the journey; keyboard-only pass per feature |
| Security | Custom + scanners | Rate limit, session fixation, CSRF, upload abuse, XSS payloads in all text fields, dependency and secret scans |
| Performance | k6 or similar | Pilot-scale load on queue, request list, search; budgets from NFRs |
| Backup and restore | Scripted drill | Restore to a new instance and verify data before go-live |

## Critical journeys (pilot)
1. Resident: register, verify email, join community, add family, submit request, see updates, accept confirmation, review after completion.
2. Operations: review request, ask for information, approve, run match, send inquiries, receive quotes, compare, shortlist, confirm booking, complete, record offline payment.
3. Vendor: log in, view inquiry, submit quote, view confirmed booking, mark complete.
4. Community admin: approve vendor and membership.
5. Security: user from community A cannot read community B data via any endpoint.
Reference fixture: "Aqualily" community, Magic Show, Saturday 17:00, 60 minutes, about 100 attendees, budget INR 10,000, Clubhouse.

## Test data
Synthetic only. Seed script builds two communities, several vendors, residents, requests in each status. Demo and test records carry an `is_test` flag excluded from metrics.

## Definition of done reference
See `MASTER_PROMPT.md` section 10. A feature is not Completed without tests at the applicable levels, regression pass and verification evidence recorded in `DEVELOPMENT_PROGRESS.md`.

## Regression
Full suite runs on every pull request; end-to-end smoke on every deploy to staging; full end-to-end nightly.

## Mutation checks (security regression guard)
Passing tests prove little if they cannot fail. For security-critical rules we periodically apply one deliberate bug at a time (open an RLS policy, skip the membership/permission/CSRF/lockout/MFA/replay/token-purpose check, store tokens in plaintext, and so on), run the suite, and require it to go red; every file is restored afterwards. Result at Milestone 2.2b: 16 of 16 caught (one initial "escape" was a flaw in the mutation script, which replaced the wrong occurrence; applied correctly the test failed). Re-run this before each release candidate and extend it with every new security rule. The script lives outside the repo for now; moving it to `tools/` is a candidate task.

## Load check (`tools/load-check.ts`, run with `check:load`)
Fills a throwaway PostgreSQL 16 with a network about 30 times the size of a pilot (30 communities, 400 vendors, 1,600 offerings, 6,000 people, 30,000 requests, 300,000 audit rows, saved lists, reviews, inquiries, reports), registers real people (with two-step sign-in where required), and times 25 screens over real HTTP, one caller at a time and then eight at once, with row-level security on. The budget is p95 400 ms for one caller and 1,200 ms for eight at once. It also refuses to run if the seeded data does not actually reach the screens it times (a timing of an empty answer proves nothing).

**What it found (before migration 0017):** the audit trail took 2,707 ms at the median and 6,860 ms at p95, and the operations request queue 338 ms and 1,329 ms, because both list the newest rows across every community and the only indexes started with the community (or the status): the database read and sorted every row (confirmed from the query plans). Two indexes fixed it: audit trail 6,860 to 55 ms, queue 1,329 to 60 ms (at p95, eight at once). A test now fails if either index is missing (caught by a mutation that removed one).

**Result now:** Measured on the development machine (one machine runs the database, the API and the client; rate limits raised so they do not hide the database), 30 communities, 400 vendors with 1,600 offerings, 6,000 people, 30,000 requests, 300,000 audit rows, about 30 times a pilot. One caller at a time, p95: every family, community and vendor screen 35 to 90 ms (catalog with every filter 60 to 90 ms), the operations queue 38 to 41 ms, the audit trail 24 ms, writing a request 52 ms and a report 35 ms. Eight at once, p95: nothing over 130 ms except sign-in (256 ms, password hashing), the operations summary (1,044 ms) and the operations "waiting for me" check (418 ms).

**What it does not tell you.** It is not a capacity test: one machine, one connection pool of 10, no network, no real browser, rate limits raised. It uses 30 times a pilot, not a launch. It seeds with triggers off, so the data is realistic in size and shape but not a record of real flows. Two screens grow in step with the number of requests, because they count every request under row-level security (about 5 microseconds a row): the operations summary (320 ms alone at 30,000 requests) and the operations "waiting for me" check (166 ms). Fine for a pilot; revisit before about 100,000 requests (keep counts in a small table updated by a trigger, the pattern used for `request_stage_flags`).
